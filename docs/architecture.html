shopping-agent 架构

输入一句话购物需求，agent 跨三平台采集真实报价、给每条报价打相关性软标签、支持按筛选条件重新决策排序——全程轨迹可回放。
一句话需求→ 意图理解→ 三平台采集→ 相关性软标签→ 用户筛选→ 购买决策 + 排序→ 建议 + 购买入口

金额计算、阈值判断、索引校验全部由确定性代码完成；LLM 只做理解、排序与建议，输出一律过 Pydantic 校验。

1LangGraph 编排：两条链路

POST /api/chat 触发全量链路；POST /api/refine 复用已采集的候选集，从 filters 节点起重新决策与排序（跳过重复采集）。StateGraph 驱动状态在节点间流转，每个节点执行都记入 trace。

2采集层：双通道 adapter

每个平台一个 adapter，统一输出 RawOffer(platform, platform_id, title, price, coupon, url, image, shop, sales, ts)。通道按配置自动选择：

平台通道一：官方联盟 API通道二：浏览器采集（默认）
京东 JD 京东联盟 jd.union.open.goods.search Kimi 浏览器扩展本地 daemon（127.0.0.1:10086）驱动用户已登录的真实浏览器：
· 京东：DOM 卡片提取（新版搜索 UI）
· 淘宝：商品链接锚点 + 卡片文本解析
· 拼多多：SSR 数据 window.rawData 直接解析
· 遇到滑块验证不绕过，提示用户手点后恢复
淘宝 TB淘宝客 taobao.tbk.dg.material.optional
拼多多 PDD多多进宝 pdd.ddk.goods.search
配了 API key 的平台优先走官方接口；两者都没有时返回空结果，绝不填充假数据。所有请求共用 daemon 锁串行执行，避免单 tab 互踩。同词查询缓存 5 分钟，降低真实采集频率。

3匹配层：七条规则打软标签

#规则判定标签
1型号不符query 含型号 token（如 y7000x）而标题缺失其他型号
2竞品query 有品牌时标题出现其他品牌（且非「适配 / 兼容」语境）其他品牌
3品牌不明query 有品牌，但标题命中不了该品牌品牌不明
4配件配件词（表带 / 贴膜 / 充电器）无主体词，或落在标题尾部区域配件
5二手翻新标题 / 店铺含「二手 · 9成新 · 95新 · 拆封 · 官翻 · 回收」疑似二手
6价格离群到手价 < 全体中位数 × 0.3（样本 ≥ 6）价格异常
7销量偏低已知销量 < 全体中位数 × 0.2（样本 ≥ 4 且阈值 > 1 件）销量偏低

全部规则只打标签，不剔除任何报价：标签由前端「排除标签」一键过滤；打标项在综合排序中自动让位于未打标报价（apply_tag_guard），并作为「标签」列透传给 LLM 供其降权。价格异常 / 销量偏低是批次相对规则，按全体中位数判定。

漏网之鱼由人工反馈兜底：页面一键「不相关」→ feedback 表永久排除。规则层评测（micro F1 0.96）与误判案例见 docs/04-metrics.md。

4可观测性：trace 全程回放

每次运行一个 trace_id

每个节点的输入、输出、LLM 原始输出、时间戳与耗时（elapsed_ms）全部落库（trace 表），通过 GET /api/trace/{trace_id} 随时回放。

前端时间线

执行轨迹可视化：节点图标 + in/out 标签 + 可折叠的 LLM 原始输出。用户能看到 agent「先搜了什么、过滤掉了什么、为什么推荐这条」。

抓取日志

crawl_log 记录每次采集的平台、成败、数量与错误——某平台缺数据可精确归因。

原始数据留存

offer 表保存过滤前的全量报价，任何过滤误杀都可以事后审计恢复。

5决策层：LLM 的边界

🧮
LLM 不算钱

价格一律取采集原值；排序下标经确定性校验，越界或缺失由代码按价格补齐。

📋
输出过 Pydantic

意图、决策、排序三个 LLM 节点的输出全部结构化校验后才进入下游。

✋
下单永远由人确认

agent 只给购买入口链接，不做自动下单 / 支付 / 退款。

🔒
不绕验证码

滑块 / 风控检测到后提示用户手点，AI 不碰。
