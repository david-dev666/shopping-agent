## 已有报价的预算调整与重新决策

### 测量场景与方法

- 使用此前真实采集的三个需求：小米手环9 NFC版、华为手环9、荣耀手环9；每组均为三平台各15条，共45条候选。
- 原始报价来自 `backend/eval/reports/decision-and-latency-20261101/complete-latency/response-001.json` 至 `response-003.json`，采集时间为 2026-10-31 23:57–23:58（北京时间）。文件哈希及原始时间保留在测量 metadata 中。
- 将原始候选保存到独立临时数据库，调用实际 HTTP `/api/refine`，使用项目配置的真实模型；没有替换模型、规则推荐或重新采集。
- 华为、荣耀的原始需求未指定版本。预跑9次中，6次先返回规格追问、3次完成模型决策；预跑全量记录保留，几十毫秒的追问响应不计入模型重新决策耗时。
- 正式预算调整测试前，为两个需澄清的需求明确模拟选择“版本不限”，保存派生快照；澄清准备单独记录，不包含在下表中。
- 对每个已确认需求依次设置250、350、450元预算，顺序执行，共9次。每次仍输入完整45条候选；以客户端单调时钟测量HTTP请求到完整JSON响应的时间，包含快照读取、规格核对、模型决策、推荐与轨迹保存。
- 记录全部响应、逐次耗时、节点轨迹与错误。统计分母固定为9次预算调整，不统计用户输入等待和平台采集时间。

## 记录与复现

`backend/eval/reports/performance-20261101/`：

- `valid-live-summary.json`、`valid-live-samples.jsonl`：本组5次完整有效查询的统计及索引。
- `live/`、`live-round3/`、`live-remaining/`：每批测量元数据及原始响应，保持原样；有效样本以索引文件为准。
- `refine-confirmed/`：9次预算调整的真实模型响应与统计，澄清准备单独保存。
- `probe/`：已有报价预跑的原始记录，不作为正式重新决策成绩。
- `bench_refine*.py.txt`：当次重新决策测量脚本快照。

实时查询使用现有 `backend/scripts/bench_live.py`，明确 `--mode chat`、live、非应用缓存，逐次保留返回体。重新决策在隔离临时数据库中保存历史真实候选，先完成版本确认，再按250、350、450元预算顺序调用 `/api/refine`。各批metadata包含源码哈希及环境，原始候选保留实际采集时间。

两组测量的输入和阶段不同，不计算严格的相对加速比例。简历分别注明三平台完整返回样本与已有报价重新决策，后续继续补充有效样本。
