# 项目定位

## 一句话

给一个商品（链接或名字），系统去多个平台问价，每天记录价格，算出历史低点，判断是否值得买，最后给出购买入口。下单的最后一步由人确认。

## 用户场景

- 我想买一个显示器，不确定现在是不是好价，也不知道三个月前最低到过多少
- 我在 A 平台看到的型号，想在 B 平台找同款，但标题完全不一样，人工对不上
- 我想知道某个商品的历史价格曲线，判断现在买还是再等等
- 我盯了几个商品，希望降价时被提醒，而不是自己天天刷

## 要解决的问题

1. 跨平台同款对不上，比价结果不可信
2. 价格没有历史沉淀，只有当前价
3. 决策靠感觉，没有数据支撑
4. 盯价靠人工刷页面

## 明确不做

- 自动下单、自动支付、自动退款
- 绕过登录、验证码、访问控制
- 大规模后台爬虫作为核心数据来源
- 用假数据填充空结果
- 让 LLM 做金额与时间的最终判断

## 与现有项目的差异

现有开源项目分两派：

- 价格追踪派（pricebuddy、price-scout）：采集和时序扎实，但基本只追踪用户粘贴的单个 URL，不做跨平台找同款
- AI agent 派（shopping-guide-agent 等）：有 LLM 编排，但不沉淀长期价格历史，本质是一次性搜索问答

本项目卡在中间：用价格追踪派的采集与存储做底座，自己补上跨平台匹配层，再套一层可观测的 agent 编排。

## 成功标准

功能标准
- 输入一个型号，能返回三个平台以上的当前价与历史曲线
- 匹配结果带置信度，低置信可人工确认
- 价格历史连续，缺失时有明确日志

工程标准
- 每个 agent 节点可追踪：调了什么工具、耗时、成本、为什么给这个建议
- 单平台采集失败不影响整体链路
- 有测试，有部署脚本

## 求职视角

面试时要能讲清楚的四件事：

1. 处理了脏数据：跨平台标题不统一、SKU 不通用
2. 沉淀了真实数据资产：连续的价格时序
3. 把 LLM 约束在可靠管道里，而不是让它自由发挥
4. 知道哪里该自动化、哪里必须留人工确认

这四点比一个花哨的自动下单 demo 有说服力。
