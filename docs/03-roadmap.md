# 路线图

原则：先做能独立验证的一小段，每阶段结束都有可看见的产出。价格曲线优先于跨平台比价，比价优先于任何下单相关。

## 阶段 0  骨架（已完成）

- 目录结构、文档、最小 FastAPI 服务
- 产出：`GET /health` 可访问

## 阶段 1  单平台采集与价格曲线

目标：一个平台，一个商品，能画出真实曲线。

- 写一个 adapter，能按商品 id 或链接拿到价格
- 建表并落库
- 定时任务每天跑一次
- 写一个查询接口，输出某商品的价格序列
- 前端画出一张曲线图

产出：一张真实商品的 30 天价格曲线。这一步做完就有可展示的东西。

验收：连续三天数据不断，缺数据时有 crawl_log 记录。

## 阶段 2  跨平台匹配

目标：同一型号在两个以上平台能对齐。

- 接第二个平台 adapter
- 实现标准化：品牌别名、型号大小写、容量写法
- 实现一级强标识匹配，跑通端到端
- 再补二级规格匹配
- 匹配结果带置信度，低置信进人工确认队列
- 写一个评估集：人工标注 50 组商品对，算匹配准确率

产出：输入一个型号，返回多平台当前价与最低价来源。

验收：评估集上强标识匹配准确率接近 100，整体不低于 90。

## 阶段 3  agent 编排与可观测性

目标：自然语言进，结构化建议出，全程可追踪。

- 用 LangGraph 搭出 intent → research → match → price → decide → recommend
- 把阶段 1、2 的能力包成工具体
- 每节点记录 trace：工具调用、token、成本、耗时
- 前端加一个 trace 视图
- 低置信或高风险时中断，等人工确认后恢复

产出：一句话询问返回带理由的建议，并能看到完整执行轨迹。

## 阶段 4  盯价与提醒

- 目标价监控，价格跌破阈值时通知
- 通知渠道先做邮件或 webhook
- 前端盯价列表与状态

## 阶段 5  打磨

- 部署：Docker Compose 一键起
- 测试补齐，采集层做失败重试与降级
- README 补两张真实数据截图
- 写一篇设计复盘，讲清楚为什么不做自动下单、为什么这么切匹配层

## 第一周日程

| 天 | 任务 | 产出 |
|---|---|---|
| Day 1 | 单平台采集跑通 | 能拿到一条真实价格 |
| Day 2 | 落库 + 定时 | 数据每天自动写入 |
| Day 3 | 画曲线 | 一张 30 天曲线图 |
| Day 4 | 第二个平台 adapter | 两个平台都能采 |

## 暂时不做

- 自动下单、支付、退款
- 服装、日用等型号不标准的品类
- 移动端
- 多用户与账号体系
