# 标题规格证据 v1

2026-10-17。此版本是“同款证据与有限补查”的第一步：先建立可检查的标题证据与确定性约束。尚未实现详情补查、自动追问或任务检查点恢复。

## 数据与边界

每条 `RawOffer` 新增可选的 `match_report`，包含原始查询、提取属性、逐字段比较、原文片段和判断原因。`source=title_rules_v1`，`sku_verified` 与 `price_verified` 始终为 false。

结构化属性包括品牌、品类、部分明确型号、手环/手表代数、版本、NFC 功能、颜色和成色。当前重点覆盖手环代数与版本以及 Y 系列 / RTX 等明确型号；不提取容量、CPU、套装、会员条件、运费或库存。不识别的字段不应被解释为已核对。

品牌沿用共享别名与兼容语境规则；不将“适配某品牌”当作商品品牌。没有 NFC/Pro 文字不等于标准版；Pro 宣传 NFC/蓝牙功能不等于两个版本；显式斜线版本、多个代数或版本则标记待确认。否定词采用有限规则识别，不是完整自然语言理解。

## 四种状态

| 状态 | 页面文案 | 语义 |
|---|---|---|
| compatible | 已识别属性一致 | 仅已提取的标题属性一致，未证明完整 SKU 同款 |
| insufficient | 规格信息不足 | 需求中的属性缺失或缺少可识别的具体型号 / 代数 |
| ambiguous | 混卖或多规格 | 无法把多个代数 / 版本或需求指定的多项属性对应到单一报价 |
| conflict | 规格冲突 | 明确属性不符，或标题声明违反需求明确排除的条件 |

字段级状态区分 consistent、conflict、unknown、ambiguous、not_requested；unknown 不视为一致，未限定的字段仍显示标题提取值。

## 推荐与接口不变量

1. 搜索、样例、Agent 和重排都生成标题证据，报价列表完整保留。
2. 标注使用用户原始需求，模型规范化搜索词不能删除用户指定的版本。
3. conflict / ambiguous 不产生首选；预算和现有警示约束仍由代码执行。
4. 可推荐候选中，已识别属性一致优先于信息不足；信息不足只能给待确认建议，不输出 buy 结论。
5. 模型收到完整标题与精简的结构化证据，不截断标题末尾的版本信息。
6. 重排 / 排序重新计算证据，不信任客户端回传的旧报告；筛选支持 `filters.match_status`，服务端与前端保持一致。
7. 前端首选卡再次检查证据状态；推荐卡、候选、对比表展示原文依据；平台摘要不将混卖 / 冲突候选作为可比报价。

**尚未绑定服务端候选快照。** 客户端仍会回传标题与报价，重新计算只避免沿用旧报告，不能证明回传内容与原始采集一致。快照 ID 与服务端存储是下一步，不能把本轮实现视为完整的防篡改链路。

## 验证

- 后端 276 项测试；本轮新增 40 项，覆盖代数 / 版本冲突、混卖、NFC 功能与否定、品牌兼容语境、字段缺失、长标题末尾、模型违规首选、重排报告重算、状态筛选及 HTTP 序列化。
- 前端 26 项测试；本轮新增 5 项，覆盖证据转义、缺失状态、首选兜底、汇总和筛选。
- 原 120 条标签开发回归不变；这些测试不是独立保留集，不构成线上同款准确率。
- wheel 冒烟检查包含 `evidence.mjs`，并验证样例响应包含证据。

## 浏览器与真实链路复核

- 样例筛选到 10 条混卖候选并更新：不产生首选购买链接；原因明确指向混卖 / 冲突，平台摘要显示暂无可比报价。
- 手机 320px / 390px 与桌面 1280px 无整页横向溢出；对比弹窗包含两份可展开证据。
- 真实查询“预算300元买小米手环9 NFC版”返回45条候选，三平台各15条；规则状态为6条已识别属性一致、18条冲突、12条混卖、9条信息不足。没有同时满足预算、警示与证据条件的候选，因此未生成首选。

上述状态数量只证明当前规则与链路运行，不是人工核对的正确率，也不能证明采集稳定性或所选 SKU 的价格。

后续优先级：服务端快照 → 需求澄清 → 限次数 / 时长的关键候选补查 → 持久化检查点与恢复 → 独立商品对评测。
