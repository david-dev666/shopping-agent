# 准确率与耗时

两块都做成**可复现**的：评测口径、脚本、标注数据都在仓库里，照着命令就能跑出同样的表。

## 1. 相关性标注的准确率

匹配层是确定性规则（不依赖 LLM），产出「软标签」而非剔除。所以这里评测的是**规则打标的准确性**。

- 开发回归集：`backend/eval/rules_eval.jsonl`，**120 条**。覆盖代数、品牌/中英文别名、明确版本冲突、配件/赠品、二手/未拆封和英文型号。
- 脚本：`cd backend && uv run python scripts/eval_rules.py --verbose`。
- 口径：逐条标题预测命中的标签，按规则统计 precision / recall / F1，micro 汇总全部标签；120 条还逐条参数化进入 pytest。

2026-10-15 本地结果：

| 规则 | P | R | F1 | TP | FP | FN |
|---|---|---|---|---|---|---|
| second_hand | 1.00 | 1.00 | 1.00 | 18 | 0 | 0 |
| rival | 1.00 | 1.00 | 1.00 | 11 | 0 | 0 |
| model_mismatch | 1.00 | 1.00 | 1.00 | 21 | 0 | 0 |
| off_brand | 1.00 | 1.00 | 1.00 | 6 | 0 | 0 |
| accessory | 1.00 | 1.00 | 1.00 | 13 | 0 | 0 |
| **micro** | **1.00** | **1.00** | **1.00** | 69 | 0 | 0 |

这是一套参与规则开发的人工构造回归样例，**不是独立保留集，也不代表线上同款匹配或推荐准确率**。原有“手环10不标型号冲突”的标注已按新能力纠正；原配件漏报、赠品误报和“未拆封”误报已有回归覆盖。

价格异常 / 销量偏低是批次相对规则，由 `tests/test_filter.py` 覆盖。规格词典仍是单一标题特征分组，无法表示完整 SKU 属性；混卖多版本、规格缺失、语义否定等仍需真实样例与结构化匹配进一步验证。

除标签回归外，后端测试覆盖预算强约束、模型输出 schema、超时/断网降级、完整候选输入、全图无 LLM 路径、不相关反馈、重排与主推荐一致性、接口并发和浏览器跨事件循环锁。前端使用 Node 原生测试验证组合筛选、排名索引、链接/文本边界、首选真实性与损坏历史数据。

```bash
cd backend
uv run pytest -q
# 回到仓库根目录，使用 Node.js 22+
cd ..
node --test frontend/tests/*.test.mjs
```

浏览器人工验证：桌面与 390px 手机布局、两件商品对比、平台筛选、筛选后推荐过期提示、重排、零结果和重置。完整浏览器 E2E 自动化、独立商品对保留集及线上 P50/P95 在 `TODO.md` 中跟踪。

## 2. 耗时

以下为旧版本本机采集记录，本轮另进行了一次真实查询验证，见下文；**尚无重复测量的新版本性能基准**。完整候选输入和 LLM 调用方式已变更，不能把旧数值当作本轮基准。

### 单平台采集（webbridge，本机实测）

命令：`cd backend && uv run python scripts/bench_crawl.py 小米手环9`

| 平台 | 耗时 | 说明 |
|---|---|---|
| 京东 | 1.5 – 3.9 s | 懒渲染，轮询到出数据 |
| 淘宝 | 2.1 – 2.7 s | 同上 |
| 拼多多 | 6 – 7 s | SSR 命中时 ≈1 s；无返回时走到 6 s 轮询上限 |

浏览器采集三平台共用单 tab 串行（`webbridge.py` 加锁），因此浏览器采集总耗时接近各平台耗时之和，联盟 API 的并发部分另计。

### Agent 端到端

一次 `POST /api/chat`（intent → research → match → filters → decide → recommend）本机实测 ≈ **15 s**，节点耗时：

| 节点 | 耗时 |
|---|---|
| research（三平台采集） | ≈ 11.1 s |
| decide（LLM 决策 + 全量排序） | ≈ 3.7 s |
| match / filters / recommend | < 50 ms |

后续节点的耗时写进 trace（`elapsed_ms`；旧记录首节点 intent 为 0，尚不能用它衡量意图解析的真实耗时），前端「执行轨迹」直接可见；未配置 LLM 时 `decide` 走确定性降级，几乎不耗时。

### 筛选重排

前端筛选面板点「更新推荐」走 `POST /api/refine`（filters → decide → recommend，**跳过采集**），本机实测：

| 场景 | 耗时 |
|---|---|
| 30 条候选 → 筛选后 6 条并重新排序 | ≈ **2.0 s**（对比全量运行 ≈15 s） |

### 口径与影响因素

- 本机（macOS）实测，随网络与平台渲染波动，只作量级参考
- 采集耗时主要由**页面渲染等待**决定（`app/adapters/webbridge.py` 的 `PAGE_READY` 轮询策略），不是网络传输本身
- 联盟 API 数据源的耗时与 webbridge 不同，未计入上表

## 3. 2026-10-16 真实链路验证

在本机通过新版 `/api/chat/stream` 查询“预算300元买小米手环9”，得到 15 条京东候选，淘宝、拼多多本次各 0 条；research 约 24.36 s、decide 约 3.68 s。页面来源为 live、推荐引擎为 llm，不是样例或直接查询缓存。此处仅为一次端到端功能验证，不作为采集成功率、P50/P95 或购买建议准确率基准。

新增回归覆盖：显式 live 绕过旧演示默认值、样例无伪造进度、SSE 事件及 Unicode 分块解码、流结束/报错、协作停止后的节点阻止、流式失败轨迹、节点耗时持久化、编辑预算覆盖旧语句、取消预算限制、选购偏好与缓存刷新。
