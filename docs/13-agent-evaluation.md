# 模型驱动的购物 Agent 与工作流评测

2026-11-01。当前智能选购依赖真实模型：需求解析和候选决策都由模型执行。模型未配置、调用失败或有限纠错后仍输出无效结构时，明确返回错误；不再生成规则排序推荐。预算、规格与数据结构校验保留为模型决策的边界。直接比价和显式固定样例仍可独立使用。

## 旧 18 组评测说明什么

旧集合覆盖预算、型号冲突、混卖、配件、二手、无合适候选六类边界，各三个变体。输入直接从候选开始，不经过模型意图解析、实际采集或多轮澄清。它主要验证最终约束能拦住错误首选，不代表 Agent 的整体理解或推荐质量。历史规则降级结果保留作版本记录，当前不再运行该模式。

## 当前主评测

新增 `backend/eval/workflow_cases.jsonl`：25 个构造场景、15 条不同需求、9 类问题。经真实 `/api/chat` 和 `/api/refine` 执行模型意图解析、标题证据、条件分支、推荐及快照续接，共 33 轮请求。只替换采集层，返回固定报价和预先设定的平台错误，不访问电商平台。

覆盖：预算边界与不同表达、型号与版本、颜色、信息缺失、配件与二手、部分 / 全部数据源失败、多个合适候选、外部指令文本、跨平台相同 ID、版本 / 代数澄清、选择不限、连续补充条件、预算修改和空筛选恢复。

预期行为在评分前写入数据文件并固定哈希，评分不调用生产匹配规则生成参考答案；每种场景可接受多个候选，不强求唯一店铺。场景为针对实现范围编写的构造数据，其中预算表达已用于修复解析问题，因此整体属于开发回归，不是独立保留集或真实 SKU 真值。

## 真实模型结果

使用项目配置的 `deepseek-chat`，每场景运行一次，未进行规则替代：

| 指标 | 结果 |
|---|---:|
| 完成的任务场景 | 25/25 |
| 符合预期的交互轮次 | 33/33 |
| 有合适候选的环节中选中合适首选 | 21/21 |
| 应不推荐的环节中不产生首选 | 7/7 |
| 应追问的环节正确提出规格问题 | 4/4 |
| 不必要的规格追问 | 0 |
| 全部数据源失败 | 1，单列，不算正确业务拒绝 |
| 最终超预算首选 | 0 |

33 轮包括首次请求和后续续接，不等于 33 条独立需求；预算在 33 轮保持预期，仅有 25 次初始意图解析。21 个可推荐环节包含信息不足时只能待确认的建议，不是实际 SKU 或购买效果正确率。原始结果见 `backend/eval/reports/agent-workflow-20261101/llm.json`。执行时的评测脚本保存为同目录 `llm_runner_snapshot.txt`，哈希与报告一致；当前脚本仅调整了注入模式的引擎标签，真实模型路径保持一致。

## 模型输出与最终约束的对照

记录同一次有效模型决策输出的第一候选，再与最终首选对照。模型收到相同的完整标题与结构化证据；比较的是最终确定性约束的作用，不是“无任何规则的模型”与另一组模型调用。

本轮 26 次有效模型决策中，原始输出有 2 次不合适首选，其中 1 次超预算；最终约束均拦截，且未强行生成替代购买建议。澄清等待和无候选环节没有模型排序，不放入这 26 次的分母。

另用固定的错误排序输出测试候选顺序扰动：每场景三个种子，共 75 次任务运行、99 轮交互。78 次注入决策中有 28 次错误首选；最终链路纠正 13 次、阻止推荐 15 次。它验证编排与约束对错误模型输出的处理，不计为真实模型能力或 75 个独立场景。原始结果见同目录 `adversarial.json`。

## 复现

在 backend 目录执行；输出文件必须不存在，评测数据库为临时库，不读写实际搜索数据。

```bash
PYTHONPATH=. .venv/bin/python scripts/eval_workflow.py --engine llm --output /tmp/shopping-agent-workflow-new.json
PYTHONPATH=. .venv/bin/python scripts/eval_workflow.py --engine adversarial --permutations 3 --output /tmp/shopping-agent-workflow-injected-new.json
```

`llm` 会调用已配置模型；未配置时拒绝运行。报告记录模型名、实际调用与用量、数据及源码哈希、逐轮响应和失败项。注入模式单独标为 `injected_output`，不充作真实模型结果。

## 并行采集的边界

当前三个浏览器平台共享 `shopping-agent` 会话和一个标签页，完整导航与提取过程持锁；联盟 API 已可并行。不能仅移除锁或增加 `gather`，否则当前页可能被另一平台导航改写。

可行的改进方向是每个平台使用独立标签页，先验证 WebBridge 能否并行调度或重叠页面加载，再将一个全局浏览器任务槽改为按标签页隔离、受限并行的资源池。需在相同需求和登录条件下对照串行 / 并行的完整率、耗时及验证码 / 超时数量。此方案尚未实现或实测，不能写成已有性能成果。
